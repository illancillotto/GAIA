## Concrete algorithm and ownership

Proposed new private module: `anomaly-worklist.ts`, adjacent to the page.
Names are provisional; final API must remain limited to this responsibility.

1. Keep classification and reason generation in a small page-owned pure
   reader. It calls `classifyCell` exactly once per input record, returns null
   for all other kinds, and calls `anomalyReasonLabel` only for anomaly/analysis
   records. No rewrite of domain rules or reason precedence.
2. Decorate each retained entry once with private sort facts: the exact
   priority score, work date and collaborator **sort name**. Preserve original
   `record`, `kind`, `reason` and reference identity. Sort name falls back to
   the empty string; collaborator-group **display name** separately falls
   back to collaborator ID. Do not conflate these two fallbacks.
3. Replace the three copied priority/tie decisions with one anomaly-domain
   comparator. It first computes the same priority subtraction and returns
   whenever `difference !== 0`. It then iterates a fixed domain table of tie
   fields: month `[date, sortName]`, day `[sortName]`, collaborator `[date]`.
   Each string comparison uses `localeCompare`, returning the first result
   with `difference !== 0`. Final result is zero.
4. Share one typed `indexAnomalyGroups(entries, recordKey)` with
   `recordKey: "work_date" | "collaborator_id"`, not an arbitrary key selector
   or extensible grouping framework. On insertion, append the original entry
   and increment `{ anomaly: 0, analysis: 0 }[entry.kind]`. This replaces two
   copied map creation/push/store loops and four repeated count filters.
5. Build distinct day and collaborator outputs from that index, with the
   existing outer ordering and fresh sorted item arrays. Shared counts are
   exposed through the current `anomalyCount`/`analysisCount` fields. Keep
   the collaborator-group comparator explicit: blocking count descending,
   group length descending, then display name.
6. Whole-month kind counts may use the same two-key counter accumulator,
   replacing two scans. Filter/first-record selection remain pure operations
   over the ordered entries; IDs and distinct dates retain Set semantics.

The actual simplification is **shared comparison policy and shared
group/count accumulation**. Decorating facts prevents repeated priority/name
resolution without introducing a cache across record/map updates. Merely
moving the current three sort bodies and two grouping loops is not acceptable.
No `sortBy` abstraction, comparator callback context, functional pipeline
framework, dynamic user-supplied fields or helper wrapper used only to hide
metrics is proposed.

## Ordering and numeric edge cases

The existing priority is exactly:

`(kind === "anomaly" ? 0 : 1) * 100000 - operational_missing_minutes`.

Do not replace it with unconditional anomaly-before-analysis ordering: an
analysis record with a very large missing value can precede an anomaly under
the current formula. Preserve zero, negatives, extreme values, infinity and
NaN where representable in the existing frontend state. In particular, NaN
must return from the priority stage, as `NaN !== 0` is true; using `||` to
combine comparator differences silently changes tie behavior.

| Surface | Outer order | Within-group / entry order |
| --- | --- | --- |
| Whole month | Priority, date, collaborator sort name | Stable source order for comparator equality |
| Day view | ISO date ascending via localeCompare | Priority, collaborator sort name; stable equality |
| Collaborator view | Anomaly count descending, total count descending, display name | Priority, date; stable equality |

Entry and Map insertion order must retain duplicate-record behavior. No new
ID tie breaker, numeric date conversion, string normalization, lowercasing,
deduplication of entries or alphabetical sort of absence causes is allowed.
Global first-critical selection still searches for a blocking kind even if
an extreme-value analysis record sorts ahead of it.
