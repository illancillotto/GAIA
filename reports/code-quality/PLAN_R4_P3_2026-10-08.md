## Recommended single responsibility

**Normalize positive-refuel averages once for all fuel-ranking consumers.**

Current `fuel_analytics` computes the same three raw averages through
`_metrics_for_logs`, then repeats identical nullable rounding decisions at
four call sites:

1. Top vehicle rows.
2. Top operator rows.
3. Operator-related vehicle rows.
4. Vehicle-related operator rows.

Exact current locations: `backend/app/modules/operazioni/routes/analytics.py:377`
(raw helper), `backend/app/modules/operazioni/routes/analytics.py:516`
(vehicle averages), `backend/app/modules/operazioni/routes/analytics.py:669`
(operator-related vehicles), `backend/app/modules/operazioni/routes/analytics.py:684`
(operator averages), `backend/app/modules/operazioni/routes/analytics.py:719`
(vehicle-related operators).

Each consumer repeats `round(price, 4) if price is not None else None`,
`round(cost, 2) if cost is not None else None`, and
`round(liters, 2) if liters is not None else None`. Twelve decisions represent
one repeated numeric convention. This is a materially stronger candidate than
moving weighted-target orchestration or merely relocating `_op_km`.

Minimal proposed design, not implemented:

- Introduce a private, immutable typed three-field `RefuelAverages` result in
  the same domain route file: `avg_price_per_liter`, `avg_refuel_cost`,
  `avg_liters_per_refuel`, each `float | None`. It is a numeric result, not a
  parameter pack, mutable context, API schema, ORM model or framework.
- Existing `_metrics_for_logs(items)` keeps its raw filtering, ordered sums
  and mean calculation, but returns these three already-normalized values.
- All four consumers use the result's fields directly. The three nullable
  rounding decisions occur once in the metrics responsibility, not four times
  in response constructors. No additional helper or new module is necessary.
- Do not replace the positive filter, introduce a single-pass statistics
  engine, rewrite net aggregation, cache identity resolution or share the
  vehicle consumption kernel with operators in this slice.

This is not a wrapper-based reduction: the duplicate arithmetic/decisions
actually disappear; all remaining decisions and any typed result declaration
must be included in the after scan. A move of the existing raw helper alone
would be `REORGANIZED_AND_CHARACTERIZED` and is not proposed.

## Behavioral invariants

- SQL statements, predicates, date defaults/granularity, query order, status
  exclusion (`open`), authorization, selected objects and transaction
  behavior remain byte-for-byte outside the numeric metrics call sites.
- The original positive set remains `_safe_float(log.liters) > 0` in arrival
  order. Storno and zero-liter logs still affect net totals/counts but not
  positive means. Missing costs remain excluded only from cost mean/count;
  their positive liters stay in the price denominator.
- No sum reassociation, sorting, rounding of individual logs or replacement
  of `sum` with a new accumulator. Price is rounded after total cost / total
  positive liters, not obtained as a mean of individually rounded prices.
- Numeric 0 stays 0, not None; no `or`-based replacement of valid averages.
  Cost/liter precision remains 2, price precision 4 and Python rounding stays
  unchanged. NaN/infinity comparisons are not repaired as a feature.
- A raw average has no other current consumer: each of the four call sites
  applies exactly the same rounding. Therefore normalization once does not
  discard a downstream raw calculation. This must be rechecked on the future
  worktree, particularly if concurrent work adds a consumer.
- Vehicle coefficient/judgement still use raw consumption before rounding;
  operator coefficient deliberately uses its already-rounded consumption.
  Weighted target, target-type precedence and judgement code remain untouched.
- WC UUID / legacy string / unknown sentinel grouping stays unchanged.
  Global operator consolidation and deliberately unconsolidated vehicle-
  related keys retain their different current semantics. No identity mapping
  or fallback is added, removed or generalized.
- Net-liter ranking, stable tie order, dictionary insertion order, top-five
  limits, labels, station grouping, related-item ordering and response schema
  do not change. The three fields contain exactly the same normalized floats.
- No added external call, mutation, repeated evaluation, test seam or
  lifecycle/concurrency mechanism. Typed construction is a private numeric
  representation and does not pass through API serialization itself.

## Alternatives explicitly not selected

- Sharing vehicle and operator consumption directly is unsafe without a
  deliberate semantic distinction: vehicle coefficient uses raw consumption,
  operator coefficient uses consumption rounded to 2. A flags-based generic
  kernel would add risk and parameter branching for a small gain.
- Operator grouping/consolidation into one new aggregate object risks changing
  floating-point reassociation: current merges add previously-summed subtotals
  and concatenate grouped log lists. Recomputing from concatenated logs is
  not guaranteed equivalent. Avoid in this slice.
- Moving `_op_km` preserves its 54 cognitive and transfers a finding; that
  alone is not improvement. Candidate-name normalization is another coherent
  possible slice, but identity fallback requires separate ownership/tests.
- Weighted-target extraction alone moves conditional debt instead of removing
  it. Stations have existing warning debt and are not this responsibility.
